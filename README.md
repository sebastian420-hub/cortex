# Cortex: a terminal coding agent

[![CI](https://github.com/sebastian420-hub/cortex/actions/workflows/ci.yml/badge.svg)](https://github.com/sebastian420-hub/cortex/actions/workflows/ci.yml)
![tests](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/sebastian420-hub/cortex/badges/tests.json)
![coverage](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/sebastian420-hub/cortex/badges/coverage.json)

Cortex is an AI agent you run in your terminal. You describe a software task; a language model
reads and searches your code, edits files, runs commands and tests, and uses git, asking before it
changes anything (unless you tell it not to). It works with a local model through Ollama, or any
server that speaks the OpenAI API (vLLM, llama.cpp, LM Studio), or a cloud model through
OpenRouter, Anthropic or DeepSeek.

What sets it apart is what happens when something goes wrong: every request can be undone, a
failed step is reported as failed, and the safety features say plainly what they do and do not
stop. See [What works and what does not](docs/STATUS.md).

> The test and coverage badges above are generated by CI from each run on `main`; no figure in
> this repository is typed by hand.

## Quick start

```bash
git clone https://github.com/sebastian420-hub/cortex.git
cd cortex
pip install .                       # Python 3.9 or newer

export OPENROUTER_API_KEY="your_key"   # the default provider
cortex                                 # start an interactive session in this directory
```

To run fully locally with [Ollama](https://ollama.ai/):

```bash
ollama pull llama3.2
cortex --provider ollama --model llama3.2
```

Other providers: `--provider anthropic` (`ANTHROPIC_API_KEY`), `--provider deepseek`
(`DEEPSEEK_API_KEY`), and `--provider openai` for a vLLM, llama.cpp or LM Studio server
(`OPENAI_BASE_URL`; see [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)). One prompt and exit:
`cortex -p "fix the failing test"`.

More options and containers: [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md). To run a task with nobody
watching, for example from a nightly schedule: `cortex run`, below.

### Optional features (all off until you ask)

| Flag | What it adds |
|------|--------------|
| `--planning` | planning tools: the model writes a list of steps and Cortex runs them in order |
| `--memory` | layered session memory; with `pip install ".[memory]"` and `semantic_memory.enabled: true`, long-term memory that persists across sessions |
| `--metacognition` | *experimental* confidence/urgency/tone note in the prompt (no evidence yet that it helps) |
| `--plan-mode` | read-only: the agent can look but not change anything or run code |
| `--auto-approve` | no prompts. Read [docs/SECURITY.md](docs/SECURITY.md) first |

## What you get

*   **Tools**: read, write and edit files; search; git; run commands and tests; fetch web pages;
    AST-based search and refactoring (Python, JavaScript, TypeScript, Java, Go).
*   **Undo that works.** `/rollback` restores the exact bytes of every file the last request
    changed through Cortex's file tools. `/undo` (and `/redo`) restores the whole project from a
    git snapshot, including what a shell command did. See [docs/SECURITY.md](docs/SECURITY.md) for
    the limits (ignored files, branch moves).
*   **Honest results.** A failed plan is reported as failed, and plan steps that are not
    implemented say so instead of passing; a one-shot run exits non-zero if the turn did not
    finish; a practice session in the gym succeeds only if the task's tests pass.
*   **Safety layers that say what they cover.** Approval prompts; a read-only PLAN mode (an
    allowlist, so a new tool is blocked until classified); a command blocklist that catches the
    well-known destructive forms; and an optional Linux sandbox
    (`command_sandbox.mode: bubblewrap`) that confines writes to the project.
*   **Memory you can see and control.** The model can `remember` a convention; `/memory list`,
    `add`, `edit` and `delete` manage what is stored. Only decisions, conventions, facts and
    summaries of solved problems are kept, not your requests or error messages.
*   **Unattended runs.** `cortex run --task "..." --verify "pytest -q" --json` does one task on its
    own git branch, checks it with your command, retries with the failure shown, and leaves you a
    branch only if the check passed. Your checkout is never touched, a run that fails leaves nothing
    behind, and budgets bound it. See [docs/HEADLESS.md](docs/HEADLESS.md) and the cron and systemd
    examples in [`examples/scheduled/`](examples/scheduled). Not yet run with a real model.
*   **A scope gate for authorized pentest work.** `cortex pentest init <dir>` scaffolds an
    engagement with a `scope.yaml` you fill in from your signed authorization; `cortex pentest
    check-scope <dir>` checks scanner output or notes against it and refuses anything not
    explicitly authorized (deny-by-default: a typo or an unlisted host never passes). It is a
    gate and an assistant for a person doing the testing, not an attack tool: it runs nothing
    against anything. See [docs/PENTEST.md](docs/PENTEST.md).
*   **A benchmark.** `python -m bench` runs 20 verifiable tasks (bug fixes and refactors) and
    records pass/fail from the tasks' own tests, plus steps, tokens and cost. See
    [docs/BENCHMARK.md](docs/BENCHMARK.md).
*   **Extensible**: hooks and plugins; see [docs/PLUGIN_DEVELOPMENT.md](docs/PLUGIN_DEVELOPMENT.md).

### Not here (yet)

An MCP server, an HTTP API or webhooks, multi-agent coordination, and a research framework are
**not implemented**; earlier versions of this README said otherwise. The
Rust and Go components are optional and off by default; the Go services have no Python client.
What is planned is in [docs/ROADMAP.md](docs/ROADMAP.md).

## Environment variables

| Variable | Purpose |
|----------|---------|
| `OPENROUTER_API_KEY` | OpenRouter (the default provider) |
| `ANTHROPIC_API_KEY` | Anthropic |
| `DEEPSEEK_API_KEY` | DeepSeek |
| `OPENAI_BASE_URL`, `OPENAI_API_KEY` | an OpenAI-compatible server (`--provider openai`); a local server needs only the URL |
| `CORTEX_OLLAMA_NUM_CTX`, `CORTEX_OPENAI_CONTEXT_WINDOW` | the context window of a local model (see [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)) |
| `CORTEX_MODEL`, `CORTEX_PROVIDER`, `CORTEX_MODE` | defaults for model, provider and permission mode |
| `CORTEX_OFFLINE=1` | never download tokenizer data (for machines without internet) |

## How it is built

*   `cortex/agent.py`: the agent loop. One user request is one *turn*, which ends with a result
    (`ok`, `error`, `max_iterations`, `loop_guard`, `blocked` or `interrupted`).
*   `cortex/tools/`: the tools. Every tool is classified (read-only, agent bookkeeping,
    mutating, runs code) in `cortex/core/tool_policy.py`.
*   `cortex/core/`: permissions and the command blocklist, undo (`transaction.py`,
    `checkpoints.py`), planning, memory, prompts, providers.
*   `bench/`: the benchmark. `tests/`: the test suite, which is offline; `tests/e2e/` drives the
    real agent loop with a scripted model.

Details: [docs/CORTEX_TECHNICAL_SPEC.md](docs/CORTEX_TECHNICAL_SPEC.md).
